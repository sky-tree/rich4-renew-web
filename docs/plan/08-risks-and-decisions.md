# 08 · 风险台账、架构决策与开发治理

## 1. 风险分级

等级：**阻断**=未解决不得公开发布相关功能；**高**=必须有试验/保护/回退策略；**中**=纳入明确阶段和回归。

## 2. Architecture Decision Records（ADR）

### ADR-001 · 采用基于 renew 的纯 Web Fork

- **日期**：2026-10-20
- **状态**：已接受的目标方案，待逐步实现。
- **背景**：项目现有规则引擎和 UI 运行于浏览器技术栈，原生版本只是 WebView/Electron 外壳。
- **决策**：Fork 到 `sky-tree/rich4-renew-web`，保留 TypeScript/Vite/DOM，逐步移除 Capacitor、Electron 发布路径。
- **替代方案**：Godot 4（规则与 UI 需重写）、C++/SDL3（Web 路线成本更高）、完全重写 Vue/React（兼容成本过高）。
- **后果**：浏览器 UI、渲染和资源管理需要专项优化；规则复用最大化。

### ADR-002 · 第一版使用现有 Canvas 2D

- **状态**：已接受的阶段性方案。
- **决策**：M1/M3 保留现有 Canvas；只有在 M4 A/B 性能验证有效后，才扩大 PixiJS/WebGL 改造。
- **原因**：已有相机、遮挡、精灵和交互逻辑；先重写会阻塞发布并扩大玩法回归。
- **后果**：第一版未必有最优 FPS，但拥有可靠的对照基线和回滚路径。

### ADR-003 · 单机游戏无需新增服务器后端

- **状态**：已接受的目标方案。
- **决策**：游戏规则与绘图在客户端，静态素材由 Nginx 提供。PeerServer/TURN 为联机专用可选组件。
- **替代方案**：WebSocket 权威游戏服务器、Spring Boot API 服务；无当前需求支撑。
- **后果**：VPS 扩容首先考虑带宽/CDN，玩法作弊防护不能依赖服务器单机规则。

### ADR-004 · 资源发布实施合法性闸门

- **状态**：已接受，构成阻断项。
- **决策**：受限原始/高清素材不得因为 GitHub Fork 或 Release 可下载而直接上传公网静态站。
- **后果**：开发和 CI 需要有无素材代码验证、已授权素材集成验证两种模式；正式页面发布由素材许可决定。

### ADR-005 · 渲染与规则独立演进

- **状态**：已接受的方向，具体 `BoardRenderer` 接口待实验验证。
- **决策**：保持 TS Core 和 RNG 决定规则与行动序列，SceneAdapter 将规则态映射到独立视图，Renderer 只负责画面呈现。
- **后果**：需要对 `board-view.ts` 做渐进接口抽离；禁止新渲染器直接改变游戏随机流。

### ADR-006 · Web 存档本地优先

- **状态**：已接受，增强待实施。
- **决策**：保留 IndexedDB 的原有手动/自动槽语义，后续支持 JSON 导入导出；云存档不列入首版。
- **后果**：用户更换设备需要自行迁移；需清晰告知存储配额与丢失风险。

## 3. 决策变更流程

新 ADR 需描述：问题、评估选项、决策、影响文件、性能/兼容证据、迁移工作量、回滚方式和日期；修改既有 ADR 时标记“已废弃/被 ADR-NNN 替代”，不要覆盖历史理由。

## 4. 上游更新和依赖维护

1. 每次合并原作者内容前记录 upstream SHA，确认是否改动 `core`、`party-net.ts`、`board-view.ts`、`bundle-assets.mjs` 等高风险模块。
2. 按功能分别建立 PR，至少运行核心测试和 Web-only 构建；浏览器实际合法素材集成测试通过后再合并。
3. 不在 Fork 中暗中删除原作者 GPL 许可、第三方署名和必要贡献说明。
4. npm 依赖大版本、PixiJS 渲染器版本、PeerJS/Coturn 协议变更均单独跟踪，不通过“顺便更新”引入。
