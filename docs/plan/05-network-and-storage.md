# 05 · 联机、存档、PWA 与安全设计

## 1. 联机系统：保留原有锁步规则

当前 `party-net.ts` 的 WebRTC / PeerJS 连接使用一个房主转发玩家回答，各客户端用同一 seed 和规则独立推进游戏。状态摘要帮助发现分叉，断线后补发回答日志，支持房主交接与超时托管。见上游 [`docs/rules/22-party-mode.md`](../rules/22-party-mode.md)。

**不做的变更**：Web-only 阶段不将普通单机游戏改为服务器计算回合；不以 Socket.IO/WebSocket 重写整个同步算法。

**必须确认的边界**：

- 派对模式最多 8 位真人（可电脑补位），大富豪 12 人是单机玩法，不能将二者混称为“12 人联机”。
- 每端都计算游戏，若随机数使用顺序、协议字段、游戏规则版本不同，可能发生状态分叉。
- 当前房间码为四位数字，便于好友使用，但不能作为强身份认证；开放房间要有访问控制与滥用保护。
- P2P 不是零服务器：需要 PeerJS 信令；跨 NAT 可需要 TURN。当前源码有第三方信令依赖和硬编码 TURN 凭据，**不得直接照搬进入公网发布版**。

## 2. 联机生产化建议

### 服务分工

| 组件 | 用途 | 部署 |
| --- | --- | --- |
| PeerServer | 房间/peer 信令交换 | VPS HTTPS 反向代理或独立受控服务 |
| STUN | 帮助双方发现公网地址 | 可用受信任的外部 STUN |
| coturn | NAT 失败时转发 DataChannel | VPS 或单独实例，按带宽监控 |
| Web 客户端 | 规则、渲染、自动保存 | Nginx 静态资源 |

### 安全要求

1. 从 `party-net.ts` 移除硬编码 TURN 长期密码；现有泄露过的凭据需在原服务端轮换。客户端拿到的 TURN 凭据本身仍可见，必须**短期有效、受配额/速率限制**；不要把持久密钥放进 Vite 环境变量（会编译进浏览器 JS）。
2. 配置 PeerJS 信令地址时支持 staging/prod 独立环境；服务使用 TLS/WSS，设置连接限制、滥用报警。
3. 比对 `protocolVersion`、`rulesVersion`、地图/资源版本及随机种子；不同版本拒绝开局或明确提示升级。
4. 对传入消息做结构/大小、序号、座位归属与权限校验，房主不能盲信客户端发来的 `ans`、`vote` 或 `chat`。
5. 房间公开列表应有数量上限、过期回收与滥用防护；断线重连重放日志要有最大长度或检查点机制。
6. 联机传输的是玩家回答和消息而非视频画面；数据量通常不大，但 TURN 中继会消耗出口带宽。

### 测试矩阵

| 场景 | 必须验证 |
| --- | --- |
| 两台设备同 Wi-Fi | 创建、加入、轮流操作、房间关闭 |
| 移动数据 ↔ 家宽 | STUN 成功/失败、TURN 回退 |
| PC ↔ iPhone/iPad | 操作同步、音效独立、版本兼容 |
| 房主离线或切后台 | 房主迁移、恢复日志顺序、不重复执行回答 |
| 玩家超时/被请出 | 自动托管、票数、回合一致性 |
| 信令/TURN 失效 | 有可理解的错误和重新连接入口 |
| 恶意/畸形消息 | 不触发崩溃、越权或无限内存使用 |

## 3. Web 存档：保留语义，移除原生文件分支

当前 `game/src/ui/saves.ts` 在浏览器使用 IndexedDB：数据库 `rich4`、store `saves`；7 个槽位中，`0` 是普通模式自动存档、`6` 是大富豪自动存档；自动档有最近 5 回合循环记录。当前代码还针对 Capacitor App 实现文件写入和旧 IndexedDB 迁移，纯 Web 版可以删除其原生相关代码，**不能误删自动保存和恢复语义**。

### 浏览器存档设计

- 保留 `readSlot`、`writeSlot`、`writeAuto`、`autoSaves`、`listSlots` 公共语义，确保旧浏览器存档能够读取。
- 引入 `schemaVersion` / `gameVersion` 兼容判断；旧格式需有明确、可测试的升级步骤，不对未来格式盲目解析。
- 导出：用户动作触发、下载 JSON；包含版本/保存时间/完整状态，可选哈希校验；文件名可包含地图和时间。
- 导入：验证文件大小上限、格式/schema、数据范围、角色和地图可用性、版本、潜在原型污染；导入前提醒覆盖并保留旧存档备份。
- **写入成功才显示“已保存”**。保留事务 `oncomplete` 语义、超时和失败提醒；不能仅凭 `put()` 发出就确认成功。
- 每次发布更新后都测试同域、相同浏览器上的历史存档；更换域名/子域意味着存档空间不同，必须支持迁移导出。
- 不将存档内容当作可以运行的脚本；导入 JSON 的文本仅以安全文本 API 显示，不直接插入未经转义的 HTML。

### 存储边界

浏览器 IndexedDB 与 Cache Storage 容量由浏览器/设备决定；可能因清理数据、隐私模式、配额限制丢失，不提供“永久不丢失”保证。云存档需要账号、后端和安全设计，目前仅作为后续选项。

## 4. 离线/PWA 阶段

**目标**：可安装的网页体验和按需离线地图，而不是首次访问强制缓存所有资源。

1. M3 发布稳定后再引入 `manifest.webmanifest`、受 `/rich4/` 范围约束的 Service Worker。
2. 第一阶段只缓存带版本的 App Shell；所有地图资源仍由 Network 或浏览器 HTTP Cache 加载。
3. 用户主动选择地图并下载离线包时：展示体积/已下载/配额评估与取消功能；分包 hash 校验，支持删除。
4. 缓存记录需绑定 buildId/资源 manifestVersion；页面和 Service Worker 更新要清理不再引用的旧包。
5. Safari / iOS 的 PWA、配额、后台恢复行为需真机验证；`navigator.storage.persist()` 不是持久性的绝对保证。
6. PWA 与联机分开定义离线能力：没有网络时可以打开已缓存的单机玩法，但不能期待 WebRTC 派对仍可创建/加入。

## 5. 隐私与基础安全

- 单机默认不上传本地存档、游戏规则事件或昵称数据到 VPS；服务器仅见正常的 HTTP 请求及必要的访问日志。
- 聊天/昵称经编码后展示，避免 DOM `innerHTML` XSS；同时限制大小、频率、控制字符。
- HTTPS、CSP（渐进引入，注意当前 `style` 和动态脚本）、X-Content-Type-Options、合适的资源 MIME 与 CORS。
- 监控日志不记录 TURN 凭据、原始存档、聊天全文、敏感鉴权头。
- Web 项目中 `VITE_*` 变量会注入客户端，不允许放任何保密信息。
- 运行时依赖和 NPM lockfile 需要持续检查供应链漏洞，依赖大版本升级单独 PR 审阅。
