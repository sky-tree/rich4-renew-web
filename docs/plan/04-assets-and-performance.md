# 04 · 素材构建、Web 加载与渲染性能计划

## 1. 性能瓶颈判断与测量先行

Web 游戏的主要压力发生在**玩家浏览器**：图片下载/解码、JS 主线程、Canvas 绘制、纹理内存、Safari WebView 进程限制。VPS 承担静态文件传输，不替用户计算 FPS。现阶段没有受控的首屏、单地图、FPS 或内存实测结果；全部数值必须先建基线。

| 维度 | 测量值/方式 | 比较基准 |
| --- | --- | --- |
| 首屏传输 | DevTools Network 的 transferred bytes、request count、缓存命中 | 清缓存首次访问与重复访问分别统计 |
| 首屏可交互耗时 | navigationStart → 可点击主菜单 | 固定网络限速、设备和浏览器 |
| 进入地图耗时 | 点击地图 → 地图首次可交互（不只是 loading 消失） | 固定地图/画风、冷热缓存 |
| 渲染性能 | 采样时间内帧时间 p50/p95/p99、>50ms 长帧、平均 FPS | 静止、滚动、旋转、特效、多人角色 |
| 浏览器内存 | `performance.memory`（仅部分浏览器）、性能工具或系统侧峰值 | 区分 JS heap、解码图片、GPU 纹理 |
| 资源 | 磁盘字节、解码后宽高、图集纹理 bytes、文件数量 | 低/中/高三档 |
| 稳定性 | 资源失败次数、context loss、黑屏、后台恢复、存档失败 | iPhone/iPad Safari 与 Android Chrome |

**建议首轮目标（非现状）**：主菜单必需初始资源 ≤10 MiB、桌面 60 FPS、手机 30–60 FPS、首屏无非当前地图大文件、关键玩法零回归。网络带宽/设备差异可能使目标调整；在取得真实基线后再锁定性能门槛。

## 2. 上游资源与文件关系

- `game/src/ui/assets.ts`：通过 `import.meta.env.BASE_URL` 构造 `assets/` URL，读取 `maps/maps.json`、`maps/remake/index.json` 和地图记录。
- `game/src/ui/sprites.ts`：读取 `orig/manifest.json`、`hd/manifest-hd.json`、`orig/outline-colors.json`；根据帧文件与 `(width,height,anchor_x,anchor_y)` 提供逻辑精灵。
- `game/src/ui/ground.ts`：`ground/index.json` → `ground/<map>/<style>/manifest.json` → 预览与 tile 资源；可视区域按需加载。
- `game/src/ui/decode.ts`：使用 Worker / `createImageBitmap` / OffscreenCanvas（浏览器可用时），失败时回退主线程。
- `game/src/ui/ground-cache.ts`：Canvas 2D 分块地面缓存；现有绘制与 `mem-tier.ts` 的内存预算相关联。
- `game/scripts/bundle-assets.mjs`：按清单复制 App 所需资源，并可将 HD PNG 转成 WebP；当前一次打包全部选用的地图和地面风格。

原仓库不包含完整素材，`game/public/assets/` 被 `.gitignore` 排除，作者额外的 Release 资源包并不包含在代码 GPL 分发授权内。**Web 版资源流水线只能处理使用者有权处理/发布的素材；不能将作者的私用资源自动公开镜像到 VPS。**

## 3. 资源分层与闭包算法（计划接口）

不要直接将文件分散到几张 zip 然后修改运行时 URL。先建立**资源依赖图**：入口 → 地图索引 → 地图记录 → 相关精灵/音乐/风格清单 → 图片实际文件；处理层级如下：

| 包 | 计划内容 | 依赖及加载点 |
| --- | --- | --- |
| `shell` | 入口、JS/CSS、字体、首页最小图片 | 页面请求时 |
| `core` | 基础角色、骰子、通用 UI/关键音效 | 对局初始化时 |
| `map-<id>` | 选定地图的规则 JSON、底图/缩略图、专属建筑与精灵 | 玩家选择地图后 |
| `ground-<id>-<style>` | 对应地图、画风的 tile 清单和切片 | 实际画风选中且进入视野时 |
| `optional-*` | 大型动画、特殊模式或低频事件音视频 | 需要时加载；单独预取 |

**依赖闭包**：

1. 读取源码约定清单及资源目录，解析实际引用关系（含动态拼接的路径和跨地图共用资源）。
2. 产生唯一、规范化的相对路径集合；跨包引用以 `core` 共用或显式 dependency 的方式处理。
3. 检测清单引用但磁盘不存在的文件；发布构建默认 **fail-fast**，不能默默略过缺文件。
4. 为每个文件生成 hash、大小、MIME、所属包，更新与之匹配的清单；不要“原文件删了但仍声明存在”。
5. 产生总览报告（文件数、总 bytes、每包 bytes、重复引用数、各格式百分比），供 PR 与 CI 对比。

示意输出（**schema 草案，尚未实现**）：

```json
{
  "schemaVersion": 1,
  "buildId": "<git-sha>",
  "packs": {
    "shell": { "files": ["main.js", "main.css"], "bytes": 0 },
    "core": { "files": [], "bytes": 0 },
    "map-0": { "files": [], "bytes": 0 },
    "ground-0-default": { "files": [], "bytes": 0 }
  }
}
```

这里的 `bytes: 0` 只是样例占位符。实际清单必须使用构建脚本测得的字节数和具体资源 URL；地图清单、原版清单、高清清单、地面清单的动态引用不能因为分包丢失。

## 4. Web 加载算法与异常处理

**目标链路**：启动只请求 Shell → 初始化通用清单及首页所需图片 → 玩家点地图 → 并发读取地图 JSON/精灵/起始区域地面 → 加载进度可见 → 开始回合 → 视野附近按需预取其他资源。

- **调度策略**：限制并行 fetch/图片解码数量；优先可见素材和临近动画、其次未来路线预取；不能让数千 PNG 同时解码。
- **本地缓存**：同一 URL 使用 Promise 去重；已经下载的图像允许在显式内存预算内复用；切地图后释放超出预算的纹理。
- **失败策略**：超时、404、损坏清单分别显示明确提示。可重试的网络错误指数退避并设上限；永久 404 不无限重试。
- **浏览器 CDN/缓存**：HTTP Cache 用于静态传输；是否做离线 Cache Storage 由 PWA 单独决定；不能假定二者缓存一致。
- **版本一致性**：入口 HTML `no-cache`/`no-store`（视发布架构），hash JS/CSS 与带版本号的资源可长期缓存；资源清单与产物版本固定绑定，避免新旧包混用。
- **跨城模式**：`loadMapData()` 只加载五城 JSON 记录，不应隐式下载五城高清底图；当前城市才需要地图画面素材。
- **预热约束**：`warmThumbs()` 目前会启动可用地图缩略图请求；需要依据实际请求流量和首屏体验决定减少数量。
- **硬编码风险**：`assets.ts:portrait()` 的高清 PNG 路径与 `RICH4_WEBP=1` 输出命名可能不一致，需补独立用例而非假设已有清单会覆盖所有路径。

## 5. 图片格式/图集优化

| 类别 | 建议 | 易错点 |
| --- | --- | --- |
| 高清角色/建筑 | WebP 质量分档（如 Q80/Q88 A/B 测试） | 透明像素、轮廓/阴影、动画帧闪烁 |
| 小图和多帧精灵 | 裁剪透明边界、按使用频率合并图集 | 必须校正 anchor 与精灵逻辑尺寸 |
| 不同 DPR | 1×/2×/4×、设备内存等级和下载模式结合 | 不改变 Game 的地图单位 |
| 地面 | 沿用/优化切片；限制一次可见/预取 tiles | GPU 最大纹理、超大画布、旋转视角 |
| 特效 | 按需求解码、释放临时纹理；限制并发 | Safari 背景前后内存恢复 |
| 音频 | 按需获取、Web Audio 解码与静音状态恢复 | 用户手势解锁；移动端切后台 |

只有在实际设备确认受支持后才引入 AVIF 或 WebGPU 路径，不能牺牲 Safari 和低端浏览器基础兼容。

## 6. 从 Canvas 2D 到 PixiJS 的阶段门槛

1. **先基准**：在同一张地图测静态地图、长距离移动、旋转/缩放、特效频繁场景的 Canvas FPS/长帧/内存/下载。
2. **分离公共逻辑**：将世界坐标、投影/逆投影、sprite 锚点、可见性、深度排序与绘图 API 解耦。
3. **单地图试验**：PixiJS 8 默认走 WebGL，使用 `RenderTexture`/TextureAtlas 评估，不全量生成场景节点。
4. **对比**：相同设备、相同画质、相同地图位置、相同角色数；冷/热缓存及多次运行；对照 screenshots 与 hit test。
5. **扩展或终止**：若在至少一个目标设备场景取得可重复、显著的性能收益，同时不使低内存设备崩溃、没有玩法回归，再推广；否则保留 Canvas，继续优先优化素材和缓存。

**注意**：GPU 图集可能提升大量小图片 draw 的性能，但可能增加常驻纹理内存。`SpriteBank` 当前 4× 资源与 Canvas 裁剪优化不能被忽略；必须严格维护释放纹理和切地图时的销毁链路。
