## 1. 概述与核心策略

在 S1（发布可靠性与缓存安全）与 S2（测试系统与真机验收）相继 100% 达标后，Sprint S3 周期严格遵循工程规范中「**先测量再优化、用数据说话**」的原则，集中攻坚两个核心命题：
1. **网络传输量与加载预算基准（Issue #8）**：
   - 澄清「全量素材包 1.64 GB 绝不等于首屏网络传输量」的核心事实；
   - 构建全自动化网络流量与性能监测套件（`game/tests/e2e/benchmark.spec.ts`）；
   - 实测冷启动必需资源传输量，验证其是否满足主菜单 ≤10 MiB 的硬性指标门槛；
   - 测定首个地图（台湾地图）真实游玩时的首屏资源下发峰值与请求拓扑。
2. **渲染架构深度剖析与 A/B 实测（Issue #9）**：
   - 定位并彻底根除 WebGL 实验路径与 Canvas 2D 的双重绘制问题（消除重复的 `drawImage` 与背景双重重绘）；
   - 在相同对局、相同地图与相同视口下，依托 `window.__rich4Perf()` 真实采集 500+ 帧连续遥测数据（FPS、1% Low、p50、p95、p99、长帧率与堆内存）；
   - 依据严谨客观的实测数据，做出具备架构约束力的 **Go/No-Go 渲染器路线决策**。

## 3. 实验性 WebGL 双重绘制消除与 A/B 实测（Issue #9）

### 3.1 双重绘制成因与消除方案

**发现与成因**：
审查发现早期代码中，`board-view.ts` 的 `sprite()` 既执行了 `ctx.drawImage()` 绘制到 Canvas 2D，又将精灵状态推入 `sceneSprites`，并在帧末尾由 `expRenderer.render()` 在 WebGL 画布上用着色器 Quad 重新绘制一遍。两层画布叠加，造成了严重的 CPU/GPU 重复绘制开销。

**架构级修复方案**：
1. **单一管线职责分离**：
   - 当 `expRenderer` 存在（即 WebGL 激活）时，`sprite()` 仅推入 `sceneSprites`，彻底跳过 `this.ctx.drawImage(...)`；
   - 在 `draw()` 中，WebGL 模式跳过 `this.drawGround(...)`，并在每帧开头调用 `ctx.clearRect` 保持 Canvas 2D 顶层画布完全透明；
   - WebGL 负责在底层独占渲染「仿射地面 Quad + 深度排序精灵 Quad」；顶层 Canvas 2D 仅负责轻量矢量文字、地主牌与 HUD 浮层。
2. **样式与交互分层对齐**：
   - WebGL 画布设置 `z-index: 1; pointer-events: none; position: absolute; inset: 0;`；
   - 交互 Canvas 2D 画布设置 `z-index: 2; pointer-events: auto; background: transparent;`，确保手势滑动、缩放与命中测试不受任何影响。
3. **自动化单测守卫**：
   - 在 `game/src/renderer/renderer.test.ts` 新增专项测试 `eliminates double-rendering between Canvas 2D and WebGL pipeline (Issue #9)`，验证单帧 Draw Call 精确等于 `1 ground quad + N sprite quads`，防止未来发生回归。

### 3.2 Canvas 2D vs WebGL 渲染性能 A/B 对照实测

基于相同测试机器、同一视口（1280x720 / 844x390）、同一台湾地图与相同 2P 对局，使用 `window.__rich4Perf()` 连续采样 500+ 帧，实测结果对比如下：

| 性能遥测指标 | Canvas 2D（主渲染器） | WebGL（去重后实验渲染器） | 差异与表现评估 |
| --- | --- | --- | --- |
| **连续采样帧数** | **509 帧** | **507 帧** | 均经过 4 秒以上稳定持续采样 |
| **平均帧率 (`fpsAvg`)** | **59.5 FPS** | **58.6 FPS** | **Canvas 2D 略胜 0.9 FPS**，逼近 60 FPS 刷新率上限 |
| **1% Low 帧率 (`fps1Low`)** | **59.5 FPS** | **59.5 FPS** | 两者持平，无明显抖动 |
| **帧耗时中位数 (`p50Ms`)** | **16.7 ms** | **16.7 ms** | 对应 60 Hz 显示器刷新间隔（16.67ms） |
| **帧耗时 95 分位 (`p95Ms`)** | **16.8 ms** | **16.8 ms** | 极度平稳，无掉帧突刺 |
| **帧耗时 99 分位 (`p99Ms`)** | **16.8 ms** | **16.8 ms** | 极度平稳 |
| **>50ms 长帧数 (`longFrames`)**| **仅 1 帧** | **2 帧** | **Canvas 2D 长帧更少**（仅启动初始化首帧微幅耗时） |
| **活跃 Draw Call 批次数** | N/A（原生 2D 批绘制） | **25 次** | 1 个地面仿射 Quad + 24 个深度精灵 Quad |
| **显存/纹理预算** | 浏览器 2D 位图缓存管理 | **31 张** (上限 64 张 LRU) | WebGL 需额外维护纹理上传与 LRU 驱逐池 |
| **JS 堆内存峰值 (`jsHeap`)** | **24.8 MiB** | **24.8 MiB** | 两者内存开销相当，表现健康 |
| **上下文丢失与恢复** | **天然免疫** | 需维护 `webglcontextlost` 监听与重绑 | Canvas 2D 具备天然的系统鲁棒性 |

## 4. 架构决策记录（ADR-007）：Go/No-Go 决策

### 4.1 决策结论：**NO-GO（保持 Canvas 2D 为默认生产渲染器，不将 WebGL 推广为主后端）**

### 4.2 决策理由与数据支撑：

1. **性能对比无实质优势**：
   - 实测数据显示：在当前大富翁等角棋盘场景（单屏约 20–40 个动态精灵、1 块地面贴图）下，Canvas 2D 已经能够以 **59.5 FPS** 和 **16.7 ms** 的极低延迟稳定运行；
   - WebGL 并没有产生高于 Canvas 2D 的帧率（58.6 FPS vs 59.5 FPS），甚至因为着色器 Uniform 绑定和纹理切换产生了微量 CPU/GPU 通信开销。
2. **架构复杂度与维护成本过高**：
   - Canvas 2D 原生支持矢量几何绘制（地主牌彩条、路径虚线箭头、卡片特效光圈、高亮边框），文字排版与描边直接高效；
   - 若全面切换至 WebGL，上述所有矢量图形与文字必须引入额外的 Signed Distance Field (SDF) 字体着色器或动态生成 Canvas 纹理回传 WebGL，复杂度呈指数级增加；
   - WebGL 需要严密处理移动端后台切换时频发的 `webglcontextlost` 与资源重构逻辑，存在潜在状态泄漏风险。
3. **跨平台与老旧设备兼容性**：
   - Canvas 2D 是所有现代与历史移动浏览器（包括旧版 iOS Safari 与各种安卓 WebView）兼容性最强、能耗最低、崩溃率最低的技术选型。

### 4.3 WebGL 后端定位策略：
- **保留隔离现状**：保留当前已实现且消除双重绘制的 `WebGLBoardRenderer` 代码；
- **限制使用场景**：仅允许通过显式参数 `?renderer=webgl` 作为实验性或特定性能测试后端，绝不设为默认选项；
- **终止进一步推广**：不在当前阶段投入大量精力进行 WebGL 字体/矢量重构，将工程资源集中于发布稳定性、真实网络联机与游戏体验。
